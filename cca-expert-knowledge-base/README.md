# TCP/QUIC 拥塞控制专家设计经验知识库：Agent 实现规范

## 1. 项目目标

### 1.1 核心目标

构建一个独立、通用、可移植的 TCP/QUIC 拥塞控制算法（Congestion Control Algorithm，CCA）领域知识库，为不同的 LLM-based 拥塞控制算法设计项目提供领域知识和专家经验支持。

知识库的核心目的不是让 LLM 盲目探索算法空间，而是帮助 LLM 学习已有专家的设计经验，包括：

- 专家面对什么网络问题时提出了某种设计。
- 专家如何分析问题及其背后的网络机制。
- 专家为什么选择某种控制机制。
- 专家考虑过哪些替代方案。
- 某种设计带来了什么收益和代价。
- 某种设计在哪些网络环境下有效或失效。
- 新的设计问题可以从已有经验中借鉴什么。

### 1.2 核心定位

本项目交付的是**拥塞控制领域专家设计经验知识库**，而不是完整的算法生成系统。

系统边界如下：

| 本项目负责       | 本项目不负责       |
| ----------- | ------------ |
| 收集领域资料      | 自动生成拥塞控制算法   |
| 提取和整理专家设计经验 | 自动进化或优化算法    |
| 建立结构化领域知识   | 设计 Agent 工作流 |
| 建立知识之间的关联   | 执行网络仿真实验     |
| 提供知识检索和访问接口 | 自动完成算法评估与部署  |
| 提供可追溯的证据来源  | 替代外部算法生成系统   |

知识库应当能够被不同的 LLM、Agent 框架和算法设计项目独立使用，不依赖某一个具体项目。

### 1.3 设计原则

1. **经验优先**：以专家设计经验为核心，而不是简单地存储论文摘要。
2. **证据驱动**：每条重要知识都应尽可能关联原始论文、RFC、源码或实验报告。
3. **推理过程显式化**：不仅记录设计结果，还要记录问题分析、机制选择和权衡过程。
4. **事实与推论分离**：不能把知识库自己的推断写成论文作者明确提出的观点。
5. **通用和可移植**：不绑定特定 LLM、Agent 框架或算法生成项目。
6. **渐进式建设**：先构建高质量的小规模知识库，再逐步扩展覆盖范围。

## 2. 知识库的核心知识模型

### 2.1 核心对象：DesignExperience

知识库应围绕 `DesignExperience`（设计经验）建立。

论文、RFC、源码和实验报告是知识的证据来源；算法是经验产生的案例；真正面向 LLM 交付的是经过整理的设计经验。

一条设计经验至少需要回答：

- 遇到了什么问题？
- 为什么这个问题值得解决？
- 专家如何理解这个问题？
- 专家选择了什么设计机制？
- 为什么选择它？
- 这个机制如何工作？
- 它有什么收益和代价？
- 它适用于什么条件？
- 有什么失败案例或限制？
- 这些结论由什么证据支持？

### 2.2 推荐数据 Schema

第一版可以使用以下 YAML Schema。实现时可以采用 JSON、JSONL、YAML 或数据库结构，但字段语义应保持一致。

```yaml
id: exp-001
title: "基于带宽估计的发送速率控制"

# 经验类型
experience_type: mechanism_design

# 设计问题背景
problem_context:
  network_conditions: []
  observed_symptoms: []
  underlying_cause: ""

# 专家设计动机和分析
design_rationale:
  motivation: ""
  problem_analysis: ""
  reasoning_chain: []

# 设计决策
design_decision:
  selected_mechanism: ""
  alternatives_considered: []
  why_selected: ""

# 机制本身
mechanism:
  description: ""
  control_signals: []
  control_actions: []
  state_variables: []

# 设计收益和代价
tradeoffs:
  benefits: []
  costs: []
  limitations: []

# 失败模式
failure_modes: []

# 适用范围
applicability:
  suitable_conditions: []
  unsuitable_conditions: []
  assumptions: []

# 参数设计经验
parameter_guidance: []

# 评估方式
evaluation:
  metrics: []
  expected_effects: []
  evaluation_conditions: []

# 证据来源
evidence:
  - source_id: ""
    source_type: paper
    locator: ""
    supports: []
    evidence_level: A

# 知识的来源属性
knowledge_status: source_reported

# 关联经验
related_experiences: []

# 元数据
metadata:
  created_at: ""
  updated_at: ""
  tags: []
```

### 2.3 关键字段说明

| 字段                    | 作用                    |
| --------------------- | --------------------- |
| `experience_type`     | 经验类型，例如机制设计、参数设计、问题分析 |
| `problem_context`     | 记录设计产生的网络背景和问题        |
| `design_rationale`    | 记录专家的设计动机和分析逻辑        |
| `design_decision`     | 记录设计选择及其理由            |
| `mechanism`           | 解释机制具体如何工作            |
| `tradeoffs`           | 记录设计收益、成本和限制          |
| `failure_modes`       | 记录可能出现的失效情况           |
| `applicability`       | 描述适用环境、不适用环境及前提假设     |
| `parameter_guidance`  | 记录参数选择及参数行为方面的经验      |
| `evaluation`          | 记录用于验证设计效果的指标和条件      |
| `evidence`            | 提供可追溯的来源证据            |
| `knowledge_status`    | 区分原始结论、综合归纳和推论        |
| `related_experiences` | 连接其他相关设计经验            |

字段允许为空。不要为了填满 Schema 而编造信息。对于来源没有提供的信息，应明确标记为未知或未报告。

## 3. 知识可信度和来源管理

### 3.1 必须区分三种知识状态

所有知识内容必须区分以下三类：

#### A. Source Reported：来源明确陈述

原始论文、RFC、源码或报告直接提供的信息。

例如：

- 某算法采用某种带宽估计方法。
- 作者明确指出某机制用于解决某个问题。
- 论文实验显示某机制在指定环境下改善了某项指标。

#### B. Cross-source Synthesis：多来源综合归纳

通过多个来源的对比、整理和归纳得到的结论。

例如：

- 多种算法都使用了某类测量信号，但采用不同的控制策略。
- 多篇研究显示某类机制在特定条件下存在相似局限。

必须记录支撑归纳的来源。

#### C. Inference：知识库推论

根据已有事实和经验进行的进一步推理。

例如：

- 某种机制可能适合某类尚未直接验证的网络环境。
- 两种机制组合可能存在潜在冲突。
- 某个设计思路可能迁移到另一类场景。

推论必须明确标记，不能冒充原始作者的结论。

### 3.2 证据等级

建议采用以下等级：

| 等级 | 含义                   |
| -- | -------------------- |
| A  | 原始论文、标准或权威技术文档中的直接证据 |
| B  | 多个独立来源相互支持的证据        |
| C  | 单一来源的间接证据或有限实验支持     |
| D  | 基于已有知识得到的推论，缺少直接验证   |

注意：证据等级和知识状态是两个不同维度。

例如，某条推论可以是 `knowledge_status: inference`，同时其推理依据来自 A 级来源。不能仅凭证据等级自动改变知识状态。

### 3.3 原始来源 Source

应建立独立的来源记录，避免在每条经验中重复保存完整的论文信息。

建议 Source Schema：

```yaml
source_id: src-001
title: ""
source_type: paper
authors: []
year: null
url: ""
doi: ""
venue: ""
version: ""

# 精确定位信息
locators:
  - type: section
    value: ""

# 与本知识库的关系
related_experiences: []

metadata:
  collected_at: ""
  notes: ""
```

支持的来源类型至少包括：

- `paper`
- `rfc`
- `code`
- `technical_report`
- `experiment`
- `other`

来源记录必须尽量保留稳定 URL、DOI、版本、章节、页码或代码路径等定位信息。

### 3.4 来源追溯要求

每条设计经验都应关联至少一个来源。

每条关键结论都应能回答：

- 结论来自哪个来源？
- 来源中的哪个章节、页面或代码位置？
- 来源实际支持的是哪一项结论？
- 这是作者明确陈述，还是知识库归纳？

不能仅仅在一条经验末尾列出若干论文，而不说明每个来源支持什么。

## 4. 知识分类体系 Taxonomy

Taxonomy 用于组织和检索知识，与数据 Schema 不同。

一条设计经验可以同时属于多个分类，不应强制只能归入一个类别。

建议第一版采用以下分类。

### 4.1 网络问题与现象

记录拥塞控制需要处理的网络问题：

- 高带宽时延积（High BDP）
- 随机丢包
- 拥塞丢包
- 浅缓冲区
- Bufferbloat
- 突发流量
- RTT 波动
- 路径变化
- 可用带宽变化
- 多流竞争
- 反向路径拥塞
- 无线网络的不可靠传输
- 数据中心网络中的低时延需求

### 4.2 设计目标与约束

记录算法设计需要实现或权衡的目标：

- 吞吐量
- 时延
- 公平性
- 收敛速度
- 稳定性
- 鲁棒性
- 带宽利用率
- 低控制开销
- 对网络变化的适应能力
- 多流共存能力

### 4.3 专家设计动机与问题分析

记录专家如何定义问题：

- 现有算法的不足
- 传统设计假设的局限
- 网络现象背后的原因
- 关键观测信号
- 问题之间的因果关系
- 设计目标之间的冲突

### 4.4 控制机制设计

记录具体的机制和设计模式：

- 带宽估计
- RTT 和时延测量
- 最小 RTT 估计
- 丢包检测和丢包响应
- ECN 信号处理
- Pacing
- 拥塞窗口控制
- 发送速率控制
- 探测机制
- 队列控制
- 增益控制
- 滤波和估计
- 状态机设计
- 启动阶段与退出阶段
- 网络状态识别

### 4.5 算法案例

将已有算法作为设计经验的案例，而不是仅作为知识库的一级内容。

可覆盖：

- TCP Reno
- CUBIC
- BBR
- Copa
- PCC
- 其他具有代表性的 TCP/QUIC 拥塞控制算法

每个算法案例重点拆解：

- 设计动机
- 核心机制
- 机制之间的关系
- 关键参数
- 设计权衡
- 适用场景
- 已知局限

### 4.6 参数与控制策略

重点记录：

- 阈值
- 增益
- 更新周期
- 探测周期
- 平滑系数
- 状态切换条件
- 参数之间的耦合关系
- 参数对吞吐、时延和稳定性的影响

### 4.7 权衡、失败模式与边界条件

重点记录：

- 吞吐量与时延的权衡
- 带宽利用率与公平性的权衡
- 快速响应与控制稳定性的权衡
- 估计误差
- 控制振荡
- 队列膨胀
- 多流不公平
- 参数敏感性
- 环境变化导致的性能退化
- 机制之间的相互干扰

### 4.8 评估方法与证据

记录：

- 性能指标
- 实验环境
- 网络拓扑
- 流量模型
- 对照算法
- 实验条件
- 测量方式
- 结果解释
- 评估局限

## 5. 知识加工流程

知识加工的目标是将原始资料转化为结构化、可追溯的专家设计经验。

建议流程：

```text
原始资料
  |
  v
资料解析
  |
  v
识别算法、问题和设计机制
  |
  v
提取专家设计动机与问题分析
  |
  v
提取设计决策与机制细节
  |
  v
提取收益、代价和适用条件
  |
  v
关联原始证据
  |
  v
区分来源结论、综合归纳和推论
  |
  v
生成 DesignExperience
  |
  v
质量检查
  |
  v
知识库存储
```

### 5.1 资料类型

第一阶段优先处理：

1. 高质量拥塞控制论文。
2. IETF RFC 和相关技术文档。
3. 具有代表性的开源算法实现。
4. 可靠的实验研究和技术报告。

可考虑的资料来源：

- IETF RFC Editor
- IETF QUIC Working Group
- 学术论文及其引用文献
- Linux TCP 拥塞控制实现
- 主流 QUIC 实现中的拥塞控制代码
- 公开实验报告

### 5.2 提取要求

Agent 在处理一份资料时，不能只生成摘要。

应重点提取以下内容：

1. 作者试图解决什么问题？
2. 作者认为现有方法的核心不足是什么？
3. 作者对网络现象有什么解释？
4. 作者提出了什么设计？
5. 设计采用了哪些机制？
6. 为什么选择这些机制？
7. 作者考虑了哪些替代设计？
8. 机制如何影响拥塞窗口、发送速率、Pacing 或其他控制变量？
9. 作者报告了哪些收益？
10. 作者报告了哪些代价或局限？
11. 设计依赖哪些假设？
12. 实验结果支持了哪些结论？
13. 哪些内容是作者明确陈述，哪些是提取者的归纳？

资料没有回答的问题应保留为空，不得自行补全为事实。

### 5.3 质量检查

每条经验入库前至少检查：

- 是否有明确的问题背景？
- 是否描述了设计动机？
- 是否说明核心机制？
- 是否解释了设计选择的理由？
- 是否记录了已知收益和代价？
- 是否说明适用条件或未知条件？
- 是否有可定位的证据？
- 是否区分事实、归纳和推论？
- 是否存在重复或语义冲突的条目？

质量不合格的内容可以保存在待审核区，但不应直接作为高可信度知识提供给 LLM。

## 6. 知识库存储与组织

第一版应优先采用简单、可维护、便于版本管理的方案。

建议逻辑上分为三层。

### 6.1 原始资料层

保存原始资料或其可追溯信息：

```text
sources/
  papers/
  rfcs/
  code/
  reports/
```

注意：涉及论文版权时，应遵守原始资料的许可和使用限制。可以仅保存元数据、摘要、合法获取的文本和定位信息，不应默认复制受版权保护的完整文档。

### 6.2 结构化知识层

保存已经整理的设计经验和来源记录：

```text
knowledge/
  experiences/
  sources/
  taxonomy/
  relations/
```

建议：

- 每条经验使用稳定 ID。
- 经验记录与来源记录分开。
- 分类信息使用统一标签。
- 关系信息通过 ID 引用。
- 支持 JSON/YAML 等机器可读格式。
- 保留修改历史，避免经验更新后丢失原始判断。

### 6.3 检索层

提供面向 LLM 的知识访问能力。

第一版可使用：

- 关键词检索
- 语义向量检索
- 元数据过滤
- 混合检索
- 关联经验扩展

不要求第一版建设复杂的知识图谱或独立的分布式检索系统。

## 7. 面向 LLM 的检索能力

### 7.1 检索目标

检索不能只返回与查询关键词相似的论文。

应尽可能返回与当前设计问题相关的专家经验。

例如，LLM 提出：

> 在随机丢包环境中，如何避免拥塞控制算法过度降低发送速率？

知识库应优先返回：

- 专家如何区分随机丢包与拥塞丢包。
- 相关算法如何判断丢包原因。
- 不同丢包响应机制的设计思路。
- 相关机制的收益与风险。
- 这些机制的适用条件和实验依据。

而不只是返回标题中包含 random loss 的论文。

### 7.2 推荐检索维度

检索应综合考虑：

- 问题背景相似性
- 网络条件相似性
- 设计目标相似性
- 控制机制相似性
- 失败模式相似性
- 适用条件
- 证据等级

### 7.3 检索结果格式

面向 LLM 的返回结果建议采用结构化格式：

```yaml
query: ""

experiences:
  - experience_id: exp-001
    title: ""
    problem_context: {}
    design_rationale: {}
    design_decision: {}
    mechanism: {}
    tradeoffs: {}
    applicability: {}
    failure_modes: []
    knowledge_status: source_reported
    evidence:
      - source_id: src-001
        locator: ""
        supports: []
        evidence_level: A

related_experiences: []

limitations:
  - ""
```

检索结果必须保留来源和知识状态。

如果检索结果主要是推论，应明确告知 LLM，不能将其当作经过实验验证的事实。

### 7.4 检索接口

实现时可以提供简单的通用接口，例如：

```python
search_experiences(
    query: str,
    filters: dict | None = None,
    top_k: int = 10
)

get_experience(
    experience_id: str
)

get_source(
    source_id: str
)

get_related_experiences(
    experience_id: str
)
```

接口只是建议，不要求使用特定语言或框架。

检索服务应与知识存储解耦，未来可以替换向量数据库或 RAG 框架，而不需要重新整理知识内容。

## 8. 第一阶段 MVP

第一阶段不追求覆盖所有拥塞控制算法，而是验证知识模型是否真正能够沉淀专家设计经验。

### 8.1 MVP 目标

完成一个小规模、可检索、可追溯的知识库。

至少包括：

1. 统一的 `DesignExperience` Schema。
2. 统一的 `Source` Schema。
3. 基础 Taxonomy。
4. 资料解析和经验整理规范。
5. 一批高质量设计经验。
6. 关键词和语义检索能力。
7. 面向 LLM 的结构化检索接口。
8. 基本的数据质量检查。

### 8.2 推荐实施顺序

**阶段一：基础结构**

- 建立项目目录。
- 定义 Schema。
- 定义知识分类。
- 定义来源记录规范。
- 准备少量代表性资料。

**阶段二：知识加工**

- 从代表性算法和论文中提取设计经验。
- 记录专家设计动机和分析过程。
- 记录机制、权衡和适用条件。
- 关联精确证据位置。
- 检查知识状态标记是否正确。

**阶段三：存储和检索**

- 实现知识记录的读取与存储。
- 实现关键词检索。
- 实现语义检索。
- 支持元数据过滤。
- 支持关联经验查询。

**阶段四：LLM 接入验证**

使用若干不同类型的拥塞控制设计问题测试知识库。

重点检查：

- 能否检索到真正相关的设计经验？
- 能否解释专家为什么采用某种机制？
- 能否提供设计收益和代价？
- 能否说明适用条件？
- 能否给出可靠的证据来源？
- 能否避免把推论说成事实？

### 8.3 MVP 验收标准

MVP 不以算法性能提升作为验收标准，因为算法生成和评估不属于本项目职责。

应以知识质量和知识可用性作为验收依据：

| 验收项    | 标准                     |
| ------ | ---------------------- |
| Schema | 经验和来源具有统一结构            |
| 可追溯性   | 重要结论能够定位到原始证据          |
| 设计经验   | 不仅记录机制，还记录设计动机和权衡      |
| 事实区分   | 能区分原始结论、综合归纳和推论        |
| 检索     | 能通过设计问题检索相关经验          |
| 结果质量   | 返回内容包含适用条件和限制          |
| 可移植性   | 不依赖特定 Agent 或算法生成项目    |
| 可扩展性   | 后续增加算法、论文和经验时不需要重构核心模型 |

## 9. 技术选型原则

Agent 应先评估成熟工具，再决定是否自行实现。

不要为了实现知识库而重复开发成熟的 RAG、向量检索和文献管理基础设施。

可优先评估：

| 类别     | 候选方案                               | 主要用途             |
| ------ | ---------------------------------- | ---------------- |
| RAG 框架 | LlamaIndex                         | 文档解析、索引、检索       |
| RAG 框架 | Haystack                           | 检索流水线和知识访问       |
| RAG 框架 | LangChain                          | 通用 LLM 数据处理和检索集成 |
| 向量数据库  | Qdrant、Chroma                      | 语义向量检索           |
| 文献元数据  | OpenAlex、Crossref、Semantic Scholar | 论文元数据和文献关联       |
| 结构化存储  | JSON/YAML、SQLite、PostgreSQL        | 经验和来源记录          |

这些是候选工具，不代表必须全部采用。

选型时重点考虑：

- 是否方便保存结构化经验？
- 是否支持元数据过滤？
- 是否支持混合检索？
- 是否能返回来源定位信息？
- 是否容易部署和维护？
- 是否容易被其他 LLM 项目调用？
- 许可是否符合项目要求？

**优先复用成熟基础设施，将开发精力放在专家设计经验的提取、结构化和质量控制上。**

## 10. 明确禁止的范围与常见偏差

Agent 实现时必须遵守以下约束：

### 不要将项目扩展成完整算法生成系统

本项目不需要：

- 自动生成 CCA 算法。
- 自动修改算法源码。
- 自动运行算法进化。
- 自动进行网络仿真。
- 自动进行性能评估。
- 自动管理算法种群或搜索空间。
- 构建复杂的多 Agent 算法设计工作流。

### 不要把知识库退化成普通论文 RAG

仅仅完成 PDF 解析、文本切块、向量化和相似度检索是不够的。

必须有专门的知识加工过程，将论文中的设计动机、推理过程、机制选择和权衡整理成结构化经验。

### 不要只记录算法结果

例如，只记录：

> BBR 使用带宽估计和 RTT 估计控制发送速率。

这只是算法机制描述，不足以构成完整的专家设计经验。

还需要进一步记录：

- 为什么需要这种估计？
- 设计试图解决什么问题？
- 估计结果如何影响控制行为？
- 为什么采用这种控制策略？
- 这种策略有什么局限？

### 不要混淆事实与推论

不能把 Agent 自己的推理写成论文作者的设计动机。

所有综合和推论都必须有明确标记。

### 不要过早追求复杂架构

第一版不需要：

- 强制使用知识图谱。
- 自研向量数据库。
- 复杂的 Agent 编排。
- 复杂的分布式服务。
- 过度设计的权限和任务系统。

优先完成高质量知识模型、经验数据和检索能力。

## 12. 给实现 Agent 的最终指令

请按照本文档实现一个独立的 TCP/QUIC 拥塞控制专家设计经验知识库。

实现时请遵守以下优先级：

1. 首先理解项目定位：本项目的核心是沉淀专家设计经验，而不是构建算法生成系统。
2. 先设计并实现统一的知识 Schema 和来源 Schema。
3. 建立能够表达设计动机、问题分析、机制选择、设计权衡和适用条件的知识结构。
4. 建立事实、跨来源归纳和推论之间的明确区分。
5. 建立知识与原始证据之间的可追溯关系。
6. 评估并复用成熟的 RAG 和存储基础设施，避免重复造轮子。
7. 实现基础知识加工、存储和检索能力。
8. 提供通用的 LLM 访问接口，不绑定具体 Agent 框架。
9. 使用少量代表性案例验证完整的数据流程和检索效果。
10. 编写测试、使用说明和架构文档。

### 实现过程中的决策要求

- 如果技术选型存在多种方案，优先选择简单、成熟、可替换的方案。
- 如果某项知识没有证据，不要编造。
- 如果论文没有明确说明设计动机，不要自行将推测写成作者观点。
- 如果某个字段没有可靠数据，允许为空。
- 如果发现已有开源项目能够满足某个基础功能，优先评估复用。
- 不要为了追求功能完整而扩大项目边界。
- 不要将知识库与某一个具体的算法生成项目耦合。

### 最终成功标准

当一个通用 LLM 面对新的 TCP/QUIC 拥塞控制设计问题时，可以通过本知识库：

1. 找到过去专家处理过的相似问题。
2. 理解专家如何分析问题。
3. 理解专家为什么选择某种机制。
4. 学习不同设计之间的收益和代价。
5. 识别设计的适用条件和失败风险。
6. 获取相关原始证据。
7. 将已有专家经验作为新设计的参考，而不是从零开始盲目探索。

**本项目最重要的产出不是存储了多少篇论文，而是沉淀了多少条高质量、可追溯、能够帮助 LLM 进行拥塞控制设计推理的专家经验。**
文档中的目录和技术选型是建议方案，应先评估复用现有工具，再决定具体实现。

## 13. 本仓库的实现

### 13.1 最快用法：零依赖 skill（推荐）

GitHub clone 后即可使用，**不需要 pip、Docker、PyTorch 或模型下载**：

```bash
git clone <repo-url> cca-expert-knowledge-base
cd cca-expert-knowledge-base

python3 skill/cca_kb.py catalog --text
python3 skill/cca_kb.py search "高 BDP、随机丢包路径上如何避免误判拥塞" --top-k 3
python3 skill/cca_kb.py get exp-001
python3 skill/cca_kb.py related exp-001
python3 skill/cca_kb.py source src-004
```

`skill/` 里只有三样东西：

```text
skill/
├── SKILL.md        # 给 LLM/Agent 的使用说明与提示词接入方法
├── knowledge.json  # 从 knowledge/ 生成的知识快照
└── cca_kb.py       # 仅用 Python 标准库的检索脚本
```

在调用 OpenAI 之前运行一次 `search`，把 JSON 结果注入 system prompt 即可。
完整示例见 [`skill/SKILL.md`](skill/SKILL.md)。

### 13.2 纯提示词模式

如果流程里不能运行脚本，直接使用静态知识包：

- `context_pack/catalog.md`：目录与摘要，先让模型挑选相关 `exp-ID`。
- `context_pack/design_experience_pack.md`：完整经验包，可直接放进 system prompt。

说明见 [`context_pack/README.md`](context_pack/README.md)。

### 13.3 目录与职责

- `schemas/`：`DesignExperience` 与 `Source` 的 JSON Schema（Draft 2020-12）。
- `knowledge/`：8 条首批设计经验（BBR、CUBIC、DCTCP、Copa、AIMD、QUIC 丢失检测、pacing、丢包信号问题分析）、10 条来源记录、标签分类与带类型的关系；**唯一事实源**。
- `sources/`：原始资料层的目录约定与版权说明（不默认提交受版权保护的全文）。
- `skill/`：零依赖运行时与 `SKILL.md`。
- `context_pack/`：由 `knowledge/` 生成的静态提示词包。
- `src/cca_kb/`：可选的完整开发栈：Schema 校验、YAML 仓库、混合检索（BM25 + 向量）、质量门禁、CLI。
- `tools/export_skill.py`：修改 YAML 后重新生成 `skill/knowledge.json` 与 `context_pack/`。
- `tests/`：Schema、fail-closed 加载、检索过滤、证据、质量门禁，以及零依赖 skill 的测试。
- `docs/`：架构、知识模型、分类、数据处理、检索说明。

### 13.4 可选：完整开发栈与容器

只有在需要重新校验 YAML、跑完整测试或使用语义向量检索时，才需要这一层：

```bash
docker build -f docker/Dockerfile -t cca-kb:dev .
docker run -d --name cca-kb --workdir /app \
  -v "$PWD:/app" -e CCA_KB_ROOT=/app \
  -e CCA_KB_EMBEDDER=sentence_transformers \
  cca-kb:dev sleep infinity
docker exec cca-kb bash -lc 'cca-kb validate --strict && cca-kb quality && pytest -q'
```

Docker 镜像内置 `intfloat/multilingual-e5-small`，因此约 2 GB；它**不是使用知识库的
必要条件**，只是开发与语义检索的可选环境。
